# Founder OS
## 最终产品需求文档（PRD）v1.0

**产品名称：** Founder OS  
**产品定位：** 创始人的 AI 组织操作系统  
**英文定位：** Founder Operating System  
**版本：** v1.0  
**文档状态：** 产品基线 / 可进入产品设计与技术方案拆解  
**日期：** 2026-11-17  
**首发用户：** AI 原生独立开发者、OPC、个人创业者、1–3 人微型工作室创始人  
**产品形态：** Desktop-first，开放式 Agent 协作与服务平台  
**核心模块：** Founder Intelligence、Agent Workspace、Agent Marketplace、Governance & Validation

# 0. 文档说明与产品决策摘要

## 0.1 文档目的

本 PRD 将 Founder OS 的产品定位、用户问题、产品原则、核心交互、功能需求、Agent 群聊、跨用户 Agent 协作、Agent 市场、治理与验证机制、数据模型、技术边界、阶段规划和验收标准统一为产品基线。

本文档用于：
- 产品与交互设计；
- 客户端、服务端、Agent Runtime 和平台工程；
- Agent 开发者生态设计；
- 测试与质量保障；
- MVP 范围控制和阶段验收。

本文档中的“必须 / 应当 / 可以”分别表示：
- **必须（MUST）**：产品验收的强制要求；
- **应当（SHOULD）**：默认要求，若不实现必须说明原因；
- **可以（MAY）**：可选能力或后续扩展。

## 0.2 一句话定义

Founder OS 是一个让创始人建立、连接、管理和协同 AI Agent 组织的开放平台。它理解创始人的目标、决策和组织约束，让来自不同开发者、不同平台和不同组织的 Agent 在统一协作空间中工作；系统负责识别值得人介入的事项、提供判断所需的信息、管理授权边界、验证执行结果，并将决策经验沉淀为可持续复用的组织能力。

## 0.3 核心产品主张

**让创始人不必亲自参与大多数工作，却仍然能够掌握目标、方向、关键决策和结果。**

Founder OS 不以“让用户管理更多 Agent”为目标，而是让用户能够组织一个由人确定目标、由多个 Agent 协作执行、由系统持续治理和验证、由人承担关键责任的 AI-native 组织。

## 0.4 四个核心产品模块

1. **Founder Intelligence（创始人智能层）**：理解创始人的目标、优先级、价值偏好、历史决策、资源约束和组织知识。
2. **Agent Workspace（Agent 协作工作空间）**：提供 Agent 群聊、任务协作、交接、讨论、交叉质询、人类参与和跨用户 Agent 邀请。
3. **Agent Marketplace（Agent 市场）**：发现、评估、安装、邀请、购买和发布由不同开发者提供的 Agent 服务与 Agent Package。
4. **Governance & Validation（治理与验证层）**：管理身份、所有权、权限、决策权、风险、预算、独立核验、审计和结果学习。

四个模块不是四个独立产品。Founder Intelligence 决定需要什么能力；Marketplace 提供能力供给；Workspace 组织能力协作；Governance & Validation 确保协作符合目标、权限和质量要求。

## 0.5 本版正式冻结的产品决策

| 决策项 | 产品决策 |
|---|---|
| 产品形态 | Desktop-first；首发优先 macOS，架构为 Windows 保留兼容性 |
| 首发用户 | AI 原生独立开发者、OPC、个人创业者、1–3 人微型工作室 |
| 核心价值 | 意图理解、注意力判断、决策准备、Agent 协作、授权治理、结果验证 |
| 人类主入口 | Workbench + Attention / Decision Case |
| Agent 协作入口 | Agent Workspace，必须包含群聊能力 |
| Agent 市场 | 属于产品长期核心模块；首发提供受控目录/私有 Agent 注册与安装基础，后续开放公开市场和商业化 |
| 外部 Agent | 必须支持通过适配器接入；后续支持邀请其他用户拥有的 Agent |
| Pachat | 可作为外部协作系统或 Agent 来源，不作为 Founder OS 核心数据后端，不形成平台锁定 |
| Agent 身份 | Agent 必须有独立身份、所有者、运行主体、版本和权限边界 |
| 人机职责 | 人负责目标、价值取舍、重大风险和边界；AI 在授权范围内自主执行 |
| 验证原则 | 执行者不能单方面证明自己完成；关键交付必须有可追溯证据 |
| 注意力原则 | 不展示所有消息；优先展示真正需要人判断或处理的事项 |
| 隐私原则 | 跨用户邀请不意味着共享 Agent 所有者的全部记忆、文件或权限 |
| 监控原则 | 不默认进行键盘、鼠标、屏幕或应用行为监控 |

## 0.6 产品成功的最终状态

用户可以在 Founder OS 中：
- 表达一个目标，系统将其转化为可执行目标、成功标准和约束；
- 将自己的 Agent、外部 Agent 和市场 Agent 组织到同一个工作空间；
- 让 Agent 在群聊中讨论、分工、质询、交接和执行；
- 让其他人的 Agent 在明确授权下参与指定项目或群聊；
- 从市场发现和使用专业 Agent 或完整工作流；
- 让系统持续观察项目、业务和 Agent 的工作变化；
- 只在目标冲突、重大风险、资源取舍或授权越界时被请求介入；
- 在 Decision Case 中快速理解事实、证据、分歧、选项和代价；
- 作出决定后，将其转化为系统规则、授权和执行任务；
- 最终获得结果验证，并将结果反馈到组织记忆和后续判断。

# 1. 产品背景与问题定义

## 1.1 AI 执行能力增强后的新瓶颈

随着 AI Agent 的执行成本下降，企业和个人可以同时启动更多 Agent、并行完成更多任务。但执行能力增强并不自动带来更好的结果，反而可能放大组织混乱。

Founder OS 聚焦四种相互关联的稀缺：

1. **目标稀缺**：知道什么值得做、为什么做、如何定义成功。
2. **验证稀缺**：知道结果是否正确、是否符合真实目标、证据是否充分。
3. **协调稀缺**：知道谁有权决定、谁负责执行、何时升级、不同 Agent 如何协作。
4. **组织知识稀缺**：关键经验、历史决策和业务上下文分散在个人头脑、文档、项目和工具中，Agent 无法可靠获得。

执行能力越强，错误目标、错误假设和权限混乱被放大的速度越快。因此 Founder OS 不应只是执行入口，而必须成为目标、协作、授权和验证的控制层。

## 1.2 目标用户的典型工作状态

典型首发用户同时经营 2–5 个项目或商业下注，使用多个模型、编码 Agent、研究 Agent、自动化工具和 SaaS 服务。其工作信息分散在：
- 本地项目目录和代码仓库；
- GitHub、终端、IDE、浏览器；
- 文档、邮件、日历和聊天工具；
- 不同模型和 Agent 的会话；
- 合作伙伴或其他开发者的 Agent；
- 用户自己的经验、判断和历史决策。

用户面临的不是简单的任务数量问题，而是：
- 不知道多个项目中什么最值得现在关注；
- 不知道 Agent 的结论是否可信；
- 反复恢复上下文和历史决策；
- 不清楚不同 Agent 是否在重复工作或相互冲突；
- 需要亲自协调每个 Agent 的职责和执行顺序；
- 不知道如何安全地使用其他人的 Agent；
- 无法判断市场上某个 Agent 是否真的具备宣传的能力；
- 重要经验没有沉淀为后续 Agent 能遵守的规则。

## 1.3 需要解决的八类摩擦

| 摩擦 | 用户表现 | Founder OS 的产品责任 |
|---|---|---|
| 目标模糊 | Agent 能执行，但任务方向不明确 | Intent Compiler，将自然语言目标转化为可执行目标和约束 |
| 注意力争抢 | 每个工具和 Agent 都要求用户查看 | Attention Engine，筛选、排序、归并和路由 |
| 上下文丢失 | 切换项目后需要重新阅读大量历史 | Context & Memory，生成项目 Brief、Resume Brief 和决策脉络 |
| 验证不足 | 执行 Agent 自称完成，但缺少证据 | Validation Architecture，独立核验和证据管理 |
| 协作混乱 | 多个 Agent 不知道听谁的、谁负责 | Agent Workspace + Authority Graph |
| 能力供给不足 | 用户无法自己构建所有专业 Agent | Agent Marketplace |
| 跨组织信任不足 | 其他人的 Agent 访问边界不清 | Identity、Ownership、Permission、Audit |
| 经验无法复用 | 相同问题反复判断、反复审查 | Policy Propagation、Decision History、Outcome Learning |

## 1.4 非目标用户

首发阶段不以以下群体为主要目标：
- 只需要单轮聊天问答的普通 AI 用户；
- 只需要传统任务看板或团队项目管理的用户；
- 希望购买单一自动化脚本、无需 Agent 组织能力的轻量用户；
- 大型企业复杂 ITSM、全量员工管理和合规采购场景。

大型企业可以成为长期市场，但首发产品不以企业管理员控制台和复杂多租户组织治理为先。

# 2. 产品原则

## 2.1 人机职责原则

人负责：
- 定义目标、价值取舍和长期方向；
- 决定重大资源配置；
- 接受重大风险；
- 定义不可委托责任和授权边界；
- 对重大商业承诺、外部承诺和不可逆操作作出最终决定。

AI 负责：
- 观察授权范围内的现实变化；
- 恢复和整理上下文；
- 调查、分析和补齐证据；
- 发现目标冲突、机会和风险；
- 构建可比较的选项；
- 在授权范围内执行、协调和处理常规异常；
- 提供独立核验材料；
- 将结果反馈到组织记忆。

**最终决策权属于人，不意味着每一步都需要人批准。** 系统必须支持常设授权和异常升级。

## 2.2 自主执行条件

Agent 只有同时满足以下条件，才可在授权范围内自主行动：
- 目标和成功标准足够明确；
- 操作在授权范围内；
- 风险和影响低于允许阈值；
- 证据足以支持行动；
- 操作可恢复、撤销或补救，或已明确接受不可逆风险；
- 结果能够被检查和验证。

以下情况必须升级：
- 目标之间存在实质冲突；
- 需要改变战略、产品范围或关键里程碑；
- 超预算、超权限或改变外部承诺；
- 涉及重大不可逆操作；
- 关键证据矛盾或不足；
- 涉及人类价值判断或不可委托责任。

## 2.3 注意力原则

每个通知、卡片、Decision Case 和交互必须回答：
1. 为什么这件事值得现在交给人？
2. 系统已经完成了哪些调查和准备？
3. 如果不处理，可能产生什么后果？
4. 人需要作出什么具体判断？
5. 判断后系统会做什么？

不得把 Agent 的所有消息、所有任务和所有状态平铺给用户。

## 2.4 证据纪律

所有重要结论必须区分：
- 已确认事实；
- 来源支持的推断；
- 未验证假设；
- Agent 之间的争议；
- 当前未知；
- 不可预测因素。

不能将多个 Agent 重复引用同一来源包装成独立证据。Agent 数量和多数意见不等于正确性。

## 2.5 规则沉淀原则

重复出现且已被确认的判断，应尽可能沉淀为：
- 架构约束；
- 自动化测试；
- 静态检查；
- 业务规则；
- Agent Policy；
- 权限规则；
- 验收标准。

避免每次任务都重新调用多个 Agent 审查同一问题。规则必须有版本、来源、适用范围、所有者和失效/复核条件。

## 2.6 开放生态原则

Founder OS 不要求所有 Agent 都由平台自研。它必须支持：
- 自有 Agent；
- 外部平台 Agent；
- 其他用户拥有的 Agent；
- 市场中购买或订阅的 Agent；
- Agent Package 和复合工作流；
- 不同模型、工具和 Harness。

通过 Agent Adapter 和统一协作协议隔离底层实现差异。

# 3. 用户、角色与核心场景

## 3.1 平台角色

| 角色 | 定义 | 核心权利 |
|---|---|---|
| Founder / Owner | 工作空间所有者或创始人 | 目标、战略、资源、授权和重大决策 |
| Workspace Admin | 被授权管理工作空间的人 | 成员、配置、Agent 接入和部分策略管理 |
| Human Member | 工作空间成员 | 按角色参与讨论、任务和项目 |
| Agent Owner / Developer | Agent 的所有者或开发者 | 管理 Agent、版本、能力、服务和计费 |
| Agent | 具有独立身份的智能执行角色 | 在授权范围内读取信息、讨论、执行和提交结果 |
| External Collaborator | 外部合作方或受邀成员 | 仅访问明确共享的空间和资源 |
| Marketplace Operator | 市场运营与审核角色 | 商品审核、投诉、下架和生态治理 |

## 3.2 Agent 的身份模型

每个 Agent 必须具备：
- 唯一 Agent ID；
- 展示名称和头像；
- 所有者/开发者；
- 运行主体（本地、云端、第三方平台或混合）；
- Agent 类型和能力声明；
- 版本号；
- 所需模型和运行环境；
- 工具和数据访问声明；
- 权限范围；
- 计费方式；
- 状态（可用、离线、暂停、撤销、已下架）；
- 评价与验证记录。

Agent 的所有权与使用权必须分离。用户购买某 Agent 的使用服务，不意味着拥有其底层代码、私有知识、模型权重或开发者资产。

## 3.3 核心使用场景

### 场景 A：多项目注意力管理
用户经营多个项目，Founder OS 识别重要变化，自动归并普通进度，只把需要人判断的事项呈现出来。

### 场景 B：多 Agent 复杂研究
用户提出一个目标，系统组织研究、专业分析、反方和核验 Agent 在群聊中协作，最终形成 Decision Case。

### 场景 C：Agent 执行与独立核验
执行 Agent 完成交付后，独立 Checker 根据需求和验收标准检查证据，不允许执行者单方面宣告完成。

### 场景 D：跨用户 Agent 协作
用户邀请合作伙伴或其他开发者的 Agent 进入项目群聊。外部 Agent 只获得本次邀请明确授予的上下文和工具权限。

### 场景 E：从市场安装专业 Agent
用户从 Agent Marketplace 发现、试用、购买并安装专业 Agent，将其加入个人工作空间或指定群聊。

### 场景 F：历史决策持续约束
创始人过去决定不接受影响核心产品发布日期的定制项目。新的销售机会出现时，系统检查资源冲突并在必要时升级。

### 场景 G：复杂任务由 Agent 自主推进
用户给出目标和边界，Agent 在授权范围内调整执行顺序、替换工具和处理常规异常；只有越界或重大风险才请求人判断。

# 4. 产品信息架构与桌面端形态

## 4.1 首发产品形态

- Desktop-first，首发优先 macOS；
- 为 Windows 保留兼容性；
- 桌面常驻但默认安静；
- 支持系统托盘/菜单栏、全局快捷键和通知中心；
- 本地项目目录优先本地处理；
- 云端模型、云端 Agent 和远程运行必须明确告知数据范围；
- 不默认录屏、监控键盘鼠标或跟踪应用使用时长；
- Web 管理界面可以作为后续补充，不替代桌面主入口。

## 4.2 主导航

建议主导航最多六个入口：

1. **Workbench**：首页、项目总览和当前焦点。
2. **Attention**：需要判断、批准、复核或稍后处理的事项。
3. **Workspace**：Agent 群聊、协作空间、成员和任务。
4. **Projects**：项目、目标、上下文、证据和历史决策。
5. **Agents**：个人 Agent、外部 Agent、运行状态、权限和交付物。
6. **Marketplace**：发现、安装、发布和管理 Agent Package。

Review、设置、连接器、账单和开发者中心放在二级入口；Review 可从 Workbench 进入。

## 4.3 Workbench 首页

首页必须在 30 秒内帮助用户回答：
- 今天最值得我亲自处理什么？
- 哪个项目出现了实质变化？
- 哪些工作 Agent 已经完成且不需要我查看？
- 哪些事项需要我的判断或批准？
- 如果我现在进入项目，之前停在哪里？
- 哪个目标或资源配置正在偏离？

首页区块：
- Focus Strip：当前焦点、专注状态和 Resume Point；
- Needs You：默认最多展示 1–3 个高价值事项；
- Portfolio：项目组合与变化摘要；
- Agent Digest：已完成、进行中、阻塞和异常的压缩摘要；
- Quick Capture：快速记录目标、机会、风险或指令。

首页不做任务看板，不以 Agent 消息数量、任务数量或更新时间排序。

## 4.4 项目卡片

每张卡片必须回答：
- 这是哪个项目 / Bet？
- 当前阶段和周期目标是什么？
- 最近发生了什么实质变化？
- 是否需要用户介入？
- Agent 正在做什么或已完成什么？
- 下一步最有价值的动作是什么？

状态：
- On Track；
- Needs Attention；
- Decision Needed；
- Blocked；
- At Risk；
- Paused；
- Quiet。

状态必须有文字和图标，不得只靠颜色表达。

# 5. Founder Intelligence：创始人意图与判断系统

## 5.1 Founder Context

系统维护以下上下文：
- Founder Intent：长期目标、阶段目标和价值偏好；
- Priority：目标优先级和冲突规则；
- Constraints：预算、时间、人员、算力、资源和风险限制；
- Decision History：历史决定、理由、证据、适用条件和结果；
- Organization Knowledge：组织角色、客户、产品、流程和业务规则；
- Authorization：常设授权、禁止事项和升级条件；
- Current Commitments：已承诺的工作、交付和外部责任。

上下文必须标注来源、时间、置信状态、所有者和版本。用户可查看、修订、撤销和导出。

## 5.2 Intent Compiler（创始人意图编译器）

### 目标
将创始人的自然语言意图、历史决策和业务判断转换为 Agent 能理解、执行、验证和持续遵守的结构化目标与约束。

### 输入
- 自然语言目标；
- 历史决策；
- 项目资料；
- 经营数据；
- 用户确认的偏好；
- 组织规则和外部承诺。

### 输出结构
- Goal：目标；
- Outcome：预期结果；
- Metric：衡量指标；
- Priority：优先级；
- Scope：适用范围；
- Constraint：资源与行为约束；
- Non-goal：明确不做的事情；
- Deadline / Review Date：期限与复核日期；
- Owner：责任人；
- Authority：允许的决策和操作；
- Escalation Condition：升级条件；
- Evidence Requirement：结果证据要求。

### 关键规则
- AI 可以提出结构化版本，但重要目标和战略约束必须由有权人确认；
- 推断出的偏好不得自动升级为永久规则；
- 规则必须支持版本、冲突检测、有效期和失效；
- 新证据可能触发规则复核，但不能静默覆盖原规则；
- 目标变化应通知受影响的项目和 Agent。

### 验收标准
- 用户输入一个自然语言目标，系统能生成结构化目标草案；
- 系统明确显示事实、推断和待确认字段；
- 用户确认后，规则能够被相关 Agent 读取；
- 规则变更可追踪、可撤销，并能识别与旧规则的冲突。

## 5.3 Decision Authority Graph（决策权关系图）

系统必须区分：
- 提议权：谁可以提出方案；
- 执行权：谁可以执行操作；
- 批准权：谁可以批准操作；
- 变更权：谁可以改变目标、预算、范围或政策；
- 复核权：谁可以核验结果；
- 最终责任：谁承担不可转移的责任。

Agent 的专业能力、群聊发言权、任务负责人身份，不自动产生批准权或目标变更权。

权限可以按工作空间、项目、任务、金额、风险、工具、资源和有效期定义。

## 5.4 Decision Case

Decision Case 是人类的主要决策交互单元，不是普通聊天消息或任务审批卡。

每个 Case 至少包含：
1. 标题与问题；
2. 为什么现在需要人介入；
3. 系统已完成的调查；
4. 目标与相关历史决策；
5. 关键事实与来源；
6. 推断、假设、未知和争议；
7. 影响范围与机会成本；
8. 可选方案及其代价；
9. 系统建议与反方观点；
10. 需要用户回答的具体问题；
11. 决策后的执行计划；
12. 授权范围、复核条件和审计记录。

Decision Case 状态：
- Draft；
- Preparing；
- Needs Human；
- Decided；
- Delegated；
- Executing；
- Verifying；
- Closed；
- Reopened。

系统不得仅以“AI 建议”要求用户点击确认。必须展示可比较选项和主要代价。

## 5.5 Attention Engine

对每条观察或事件评估：
- 对目标的影响；
- 时间敏感性；
- 风险严重度；
- 可逆性；
- 证据质量；
- 是否超出授权；
- 是否与当前焦点冲突；
- 延迟处理的代价。

通知等级：
- N0：静默记录；
- N1：摘要；
- N2：进入 Attention 队列；
- N3：即时通知或需要人处理。

等级由风险和用户策略决定，不能仅按 Agent 主观紧急程度决定。

## 5.6 Knowledge on Demand

系统只在具体判断需要时补齐知识：
- 先自动检索已授权项目资料和外部来源；
- 提供与当前决策直接相关的概念、规则和案例；
- 区分事实来源与模型解释；
- 展示关键不确定性；
- 不把 Founder OS 做成通用百科或课程平台。

## 5.7 Allocation Review

支持用户周期性复核：
- 时间和资源分配；
- 项目优先级；
- 当前承诺；
- 机会成本；
- 目标偏离；
- 暂停、继续、加码或转向方案。

系统可以建议资源调整，但重大资源重新分配必须由有权人确认。

# 6. Agent Workspace：Agent 群聊与协作工作空间

## 6.1 产品定位

Agent Workspace 是多个 Agent、人类成员和外部协作者共同完成工作的协作空间。它必须支持 Agent 群聊，但不能退化为一个消息堆积的普通聊天软件。

群聊是协作现场；Decision Case 是创始人的关键判断入口。两者并存，职责不同。

## 6.2 Workspace 类型

- Personal Workspace：个人工作空间；
- Project Workspace：围绕一个项目；
- Task Room：围绕一个具体任务或决策；
- Shared Workspace：多个用户/组织共同参与；
- Agent Service Room：围绕外部 Agent 服务的协作空间。

一个群聊可以关联一个或多个项目、目标、Decision Case 和任务。

## 6.3 群聊核心能力

P0 基础能力：
- 创建群聊；
- 添加/移除自有 Agent；
- 添加人类成员；
- Agent 发言和人类发言；
- @ 指定 Agent 或成员；
- 消息引用、回复和线程；
- 群聊上下文和附件；
- 消息来源与 Agent 身份展示；
- 将讨论转为任务；
- 任务负责人和交付标准；
- 结构化结果提交；
- 群聊搜索；
- 关键决定标记；
- 任务与 Decision Case 关联。

P1 能力：
- 邀请其他用户拥有的 Agent；
- Agent 间自动交接；
- 多 Agent 并行调查；
- 交叉质询和反方审查；
- 自动生成讨论摘要、分歧和未决事项；
- 群聊模板和角色模板；
- 外部 Agent 的可见性与权限控制；
- 语音/多模态消息按平台能力扩展。

## 6.4 群聊不是无边界自由讨论

每个群聊应有：
- 目标；
- 关联项目；
- 参与者；
- Agent 角色；
- 协作模式；
- 任务和验收标准；
- 可访问的资料范围；
- 可调用的工具；
- 授权策略；
- 完成条件；
- 保留期限。

系统应支持不同协作模式：
- Open Discussion：开放讨论；
- Structured Debate：结构化辩论；
- Research Panel：多 Agent 调查；
- Execute & Verify：执行与独立核验；
- Workflow Run：按预设流程协作；
- Human Decision：需要人类裁决。

## 6.5 Agent 群聊行为规则

- Agent 必须以明确身份发言，不允许伪装成其他 Agent 或人类；
- Agent 应声明自己是提出建议、报告事实还是提交执行结果；
- 关键事实必须附来源或证据引用；
- Agent 可以质疑其他 Agent，但应指出具体结论、证据缺口或逻辑问题；
- 多数意见不能自动变成决策；
- Agent 不得因被 @ 就获得额外工具或数据权限；
- 群聊中的消息、文件和外部内容均视为不可信输入，必须防范提示词注入；
- 讨论结论不能自动覆盖 Founder Intent 或历史决策；
- Agent 可以提出授权申请，但不能自行扩大权限。

## 6.6 协作任务对象

每个任务至少包含：
- Task ID；
- 目标；
- 背景和上下文；
- 发起者；
- 负责人 Agent / 人；
- 参与 Agent；
- 输入资料；
- 交付物；
- 验收标准；
- 预算和截止时间；
- 权限范围；
- 状态；
- 证据；
- 核验者；
- 结果。

任务状态：
- Proposed；
- Ready；
- Assigned；
- Running；
- Waiting；
- Blocked；
- Submitted；
- Verifying；
- Accepted；
- Rejected；
- Cancelled。

## 6.7 执行与核验分离

重要任务必须支持独立核验：
- 执行 Agent 提交交付物、变更记录和自检结果；
- Checker Agent 按原始目标和验收标准核验；
- Checker 应尽可能独立于执行 Agent；
- 核验结果包括 Verified、Not Verified、Blocked、Out of Scope；
- 证据不足不得标记为 Verified；
- 失败项可返回修复；
- 高风险交付由人最终确认。

不能把“执行 Agent 说完成”当作完成证据。

## 6.8 人类介入方式

人类成员可以：
- 旁观群聊；
- 参与讨论；
- 补充事实；
- @ 指定 Agent；
- 修改任务目标；
- 暂停或取消任务；
- 批准越权请求；
- 作出 Decision Case 决策；
- 纠正 Agent 对历史决策或业务事实的理解。

人类不应被要求逐条确认 Agent 的普通消息或低风险交接。

## 6.9 群聊与 Decision Case 的关系

当群聊出现以下情况时，Founder OS 可以生成 Decision Case：
- Agent 发现目标冲突；
- 多个 Agent 的结论分歧会改变行动；
- 需要重大资源取舍；
- 需要改变产品或商业方向；
- 需要超出常设授权；
- 证据不足且关键事实只能由创始人提供；
- 涉及重大风险或不可逆操作。

Decision Case 必须引用原始群聊、任务和证据，但不应要求用户阅读完整聊天记录。

# 7. 跨用户 Agent 邀请与跨组织协作

## 7.1 产品目标

允许用户邀请其他人拥有或运营的 Agent 参与指定群聊、项目或任务，使 Agent 能跨用户、跨组织协作。

这不是共享一个账号，也不是把 Agent 所有者的所有数据开放给邀请方。

## 7.2 邀请模式

- Invite by Owner：Agent 所有者主动邀请自己的 Agent；
- Invite by Workspace Member：成员向外部 Agent 所有者发出邀请；
- Marketplace Agent：从市场选择并按许可调用；
- Temporary Guest Agent：仅在特定群聊/任务中临时参与；
- Organization Agent：由组织管理员部署并授权。

## 7.3 外部 Agent 的授权流程

1. 邀请方选择 Agent 和参与空间；
2. 系统展示 Agent 所有者、开发者、能力、运行位置和所需权限；
3. Agent 所有者或有权管理员确认参与；
4. 双方确认可访问的上下文、文件、工具和预算；
5. 生成有范围、有期限的授权凭证；
6. Agent 加入指定群聊；
7. 系统记录访问和操作审计；
8. 任务结束、授权过期或任一方撤销后，权限失效。

## 7.4 权限最小化

默认只授予：
- 当前群聊消息；
- 明确附加的文件；
- 明确指定的项目资料；
- 明确授权的工具；
- 当前任务所需的最小上下文。

默认禁止：
- 读取 Agent 所有者的私人记忆；
- 读取邀请方全部项目；
- 访问未授权文件和连接器；
- 访问其他群聊；
- 代表所有者签署合同或作出商业承诺；
- 未经授权持续保留数据访问；
- 将群聊内容用于训练或其他用途，除非双方有明确、单独的授权。

## 7.5 所有者控制

Agent Owner 必须能够：
- 查看 Agent 参与的空间；
- 查看其访问的资源类别；
- 查看执行记录和费用；
- 限制可加入的工作空间；
- 设置可接受的任务类型；
- 设置价格和预算；
- 暂停或撤销 Agent；
- 管理版本和更新；
- 处理用户投诉。

## 7.6 跨组织信任机制

平台必须提供：
- 所有者身份验证；
- Agent 身份验证；
- 授权范围和有效期；
- 可撤销凭证；
- 操作审计；
- 数据隔离；
- 费用上限；
- 速率限制；
- 访问异常告警；
- 争议处理与投诉机制。

跨组织 Agent 协作属于高风险能力，必须在安全模型和权限模型完成后开放，不得先开放无边界共享再补治理。

# 8. Agent Marketplace：Agent 市场

## 8.1 产品定位

Agent Marketplace 是发现、评估、购买、安装、配置和发布专业 Agent 服务及 Agent Package 的市场。

市场商品不应只是 Prompt 或模型聊天入口，而应描述可交付的能力、运行条件、权限需求、质量证据和价格。

## 8.2 Agent 商品类型

1. **专业能力 Agent**：市场研究、财务分析、法律资料研究、用户研究、产品分析、技术架构等。
2. **执行型 Agent**：编写代码、制作设计、处理文件、分析数据、运营和业务流程。
3. **核验型 Agent**：代码审计、合同核验、数据验证、交付验收和质量检查。
4. **管理与决策 Agent**：战略分析、经营分析、资源规划、风险识别和项目协调。
5. **Workflow Package**：多个 Agent、工具、规则和流程组成的完整工作系统。

## 8.3 Agent Package 商品结构

每个商品必须声明：
- Package ID；
- 名称、描述、类别和开发者；
- Agent Identity；
- 版本；
- 能力范围；
- 不具备的能力；
- 模型要求；
- 运行环境；
- 工具清单；
- 数据访问要求；
- 知识和 Skills；
- 工作流定义；
- 输入和输出格式；
- 质量测试和评估结果；
- 已知限制；
- 安全与权限声明；
- 定价和计费方式；
- 更新日志；
- 支持和维护承诺；
- 评价、投诉和下架状态。

## 8.4 市场核心功能

### 买家侧
- 分类浏览和搜索；
- 按任务、行业、能力和运行环境筛选；
- 查看能力说明、限制、权限和价格；
- 查看测试结果和真实任务表现；
- 免费试用或沙盒试用；
- 安装到个人或项目工作空间；
- 邀请 Agent 进入指定群聊；
- 配置模型、工具和知识；
- 管理订阅、用量和预算；
- 更新、回滚、停用和卸载；
- 查看费用和使用记录。

### 开发者侧
- 开发者资料与身份验证；
- 创建和发布 Agent Package；
- 版本管理；
- 能力和权限声明；
- 上传测试集和评估报告；
- 设置价格和许可；
- 管理试用和订阅；
- 查看使用量、收益和评价；
- 发布更新；
- 回应投诉；
- 暂停或下架商品。

### 平台侧
- 商品审核；
- 恶意行为检测；
- 权限和数据声明检查；
- 沙盒和测试环境；
- 版本和依赖管理；
- 评分与评价治理；
- 退款和争议处理；
- 开发者收益结算；
- 商品下架和安全响应。

## 8.5 市场评价体系

不能仅以下载量、星级和宣传语评价 Agent。

应逐步建立：
- 任务类型；
- 测试集和测试版本；
- 成功率；
- 失败率和失败类型；
- 证据质量；
- 响应时间；
- 平均成本；
- 人工接管率；
- 用户反馈；
- 版本稳定性；
- 权限合规情况。

评价必须区分：
- 开发者自测；
- 平台自动测试；
- 独立第三方测试；
- 真实用户任务表现。

不得将小样本或单一场景表现宣传为普遍能力保证。

## 8.6 商业模式

支持但不限于：
- 免费；
- 一次性购买；
- 月度/年度订阅；
- 按调用量；
- 按任务；
- 按运行时长或资源消耗；
- 工作流 Package 订阅；
- 企业私有部署许可。

平台可收取交易服务费或市场分成。具体费率、支付地区和结算规则属于商业验证项，不在本 PRD 冻结。

## 8.7 市场安全规则

- Agent Package 必须声明真实能力和权限；
- 未经审核不得请求与功能无关的敏感权限；
- Agent 不得隐蔽外传用户数据；
- Agent 不得利用群聊或文件内容进行提示词注入和越权；
- 版本更新必须展示权限变化；
- 重大权限变化必须重新授权；
- 用户可停用、卸载和撤销权限；
- 平台保留紧急下架和安全隔离能力；
- 开发者必须说明数据处理、日志保留和第三方依赖。

# 9. Governance & Validation：治理与验证系统

## 9.1 Identity & Ownership

平台必须区分：
- 人类用户身份；
- 工作空间身份；
- Agent 身份；
- Agent 所有者；
- Agent 运行主体；
- 开发者身份；
- 外部协作者身份。

身份不能仅由显示名称确定，关键操作必须绑定可验证主体。

## 9.2 Permission Model

权限至少包括：
- Read：读取；
- Write：写入；
- Execute：执行工具或任务；
- Delegate：委托其他 Agent；
- Approve：批准；
- Publish：发布；
- Purchase：购买；
- Share：共享；
- Administer：管理；
- Change Policy：改变规则或授权。

权限范围可以按：
- 工作空间；
- 项目；
- 群聊；
- 任务；
- 文件；
- 工具；
- 金额；
- 操作类型；
- 风险等级；
- 时间有效期。

## 9.3 授权等级

- Level 0：只读观察；
- Level 1：分析和建议；
- Level 2：创建草稿和内部任务；
- Level 3：在限定范围内执行可恢复操作；
- Level 4：执行具有外部影响的操作，需明确审批或专项授权；
- Level 5：改变战略、权限、预算或重大不可逆事项，必须由指定人类权责主体决定。

等级仅作为统一描述，不替代具体操作级权限校验。

## 9.4 风险分级

风险评估维度：
- 影响范围；
- 可逆性；
- 财务影响；
- 外部承诺；
- 数据敏感性；
- 安全影响；
- 目标冲突；
- 证据充分性。

高风险操作包括但不限于：
- 对外发送报价、合同或承诺；
- 付款、采购和资金转移；
- 删除重要数据；
- 发布生产变更；
- 修改权限或共享敏感资料；
- 变更战略、预算和关键项目范围。

## 9.5 Validation Architecture

验证分四层：

| 层级 | 验证内容 | 主要方式 |
|---|---|---|
| L1 执行验证 | 操作是否成功执行 | 工具返回、日志、自动测试 |
| L2 交付验证 | 交付物是否符合要求 | 验收标准、独立 Checker |
| L3 目标验证 | 结果是否实现目标 | KPI、用户反馈、业务数据 |
| L4 战略验证 | 事情是否仍值得做 | 机会成本、战略复核、人类判断 |

验证不等于无限增加 Agent Review。重复且明确的问题优先沉淀为静态检查、测试、架构规则和 Policy。

## 9.6 审计与可追溯

系统必须记录：
- 谁发起；
- 哪个 Agent 执行；
- 使用了什么权限；
- 读取或修改了哪些资源类别；
- 调用了哪些工具；
- 输入和输出摘要；
- 关键证据；
- 谁批准；
- 结果是什么；
- 何时撤销或修改授权。

日志应遵循数据最小化原则，避免无必要保存敏感原文。

## 9.7 安全与提示词注入

- 外部消息、网页、文件、代码和 Agent 输出均视为不可信数据；
- 工具权限由 Policy Engine 控制，不由模型自行决定；
- Agent 不得通过自然语言要求提升权限；
- 跨用户 Agent 使用隔离凭证；
- 高风险工具执行前必须在服务端再次校验；
- 模型输出不得直接修改关键系统状态；
- 关键状态变更必须经过规则验证和权限检查；
- 支持暂停、撤销和紧急隔离。

# 10. Agent Adapter 与开放协议

## 10.1 设计目标

Founder OS 不绑定单一 Agent 平台。所有外部 Agent 通过 Adapter 接入，统一身份、任务、消息、证据、权限和结果格式。

## 10.2 Adapter 类型

- Native Agent Adapter：Founder OS 原生 Agent；
- MCP Adapter：通过 MCP 接入工具或 Agent 能力；
- API Adapter：通过公开 API 接入；
- Webhook Adapter：事件推送和回调；
- CLI / Harness Adapter：本地命令行或开发 Harness；
- Pachat Adapter：在接口允许的范围内连接 Pachat 协作空间；
- Manual / Human Relay Adapter：无自动接口时由用户手动交接；
- Future Protocol Adapter：兼容未来 Agent 通信协议。

## 10.3 统一 Agent Contract

每个接入 Agent 应提供：
- identity；
- owner；
- capabilities；
- runtime；
- availability；
- permission requirements；
- task input schema；
- output schema；
- evidence references；
- cost metadata；
- cancellation behavior；
- health status；
- version。

## 10.4 不假设外部平台具备能力

如果外部平台没有稳定 API、Webhook、事件订阅或数据导出能力：
- 不得声称支持实时双向控制；
- 可以采用人工交接、Agent 自身 MCP 或受控轮询；
- 必须明确同步延迟和失败模式；
- Founder OS 的核心数据仍保存在自身系统；
- 必须允许替换外部协作平台。

Pachat 是可接入的协作层或 Agent 来源，不是 Founder OS 的唯一消息总线、身份系统或决策数据库。

# 11. 核心数据模型

以下为逻辑数据对象，不等同于最终物理数据库设计。

| 对象 | 核心字段 / 内容 | 用途 |
|---|---|---|
| User | user_id、身份、偏好 | 人类用户 |
| Workspace | workspace_id、owner、成员 | 协作空间 |
| Project | project_id、目标、阶段、状态 | 项目上下文 |
| FounderIntent | 目标、优先级、适用范围 | 创始人意图 |
| Constraint | 类型、阈值、有效期、来源 | 行为和资源约束 |
| Policy | 规则、条件、动作、版本 | 可执行治理规则 |
| Decision | 决定、理由、证据、结果 | 决策历史 |
| DecisionCase | 问题、选项、证据、状态 | 人类判断单元 |
| AuthorityGrant | 主体、权限、范围、期限 | 授权 |
| AgentIdentity | Agent ID、Owner、Runtime、Version | Agent 身份 |
| AgentPackage | 能力、依赖、权限、价格 | 市场商品 |
| AgentInstallation | 安装者、配置、版本、状态 | 用户安装实例 |
| AgentSession | 运行实例、状态、成本 | Agent 运行 |
| Conversation | 群聊空间、成员、关联项目 | 群聊 |
| Message | 发送者、内容、引用、时间 | 消息 |
| Task | 目标、负责人、验收、状态 | 协作任务 |
| Assignment | Agent、角色、权限、任务 | 分工 |
| Evidence | 来源、类型、时间、完整性 | 证据 |
| Verification | 核验者、标准、结果 | 独立核验 |
| Observation | 外部变化、来源、影响 | 现实感知 |
| Outcome | 结果、指标、偏差 | 结果学习 |
| AuditEvent | 主体、操作、资源、时间 | 审计 |
| UsageLedger | 调用量、费用、归属 | 计费 |

## 11.1 数据关系原则

- Agent Identity 与 Agent Package 分离：同一 Agent 技术可以有多个发布版本和安装实例；
- Agent Owner 与 Agent User 分离：使用权不等于所有权；
- Conversation 与 Task 分离：聊天讨论可以产生任务，但任务不是聊天消息；
- DecisionCase 与 Decision 分离：待决策事项与最终决定分别记录；
- Evidence 与 Agent Message 分离：证据必须可独立引用，不以消息文本替代；
- Authorization 与 Role 分离：角色模板不能代替具体权限；
- Policy 与 FounderIntent 分离：意图表达目标，Policy 表达可执行约束；
- Outcome 与 Task Completion 分离：任务完成不等于商业目标达成。

# 12. 核心用户流程

## 12.1 初始化与上下文建立

1. 用户创建个人 Workspace；
2. 设置核心目标和当前项目；
3. 授权读取选定项目目录或数据源；
4. 导入已有 Agent 或连接外部 Agent；
5. 系统生成 Founder Context 初稿；
6. 用户确认关键目标、约束和历史决策；
7. 系统展示可用能力、权限和数据范围；
8. 用户完成首个 Agent Workspace 配置。

初始化不得要求用户手工填写大量结构化资料。系统先读取授权来源、生成草案，再让用户确认关键事实。

## 12.2 发起复杂任务

1. 用户自然语言描述目标；
2. Intent Compiler 识别目标、约束和缺失信息；
3. 系统建议协作模式和 Agent 角色；
4. 用户选择或确认 Agent；
5. 系统创建 Agent 群聊和任务；
6. Agent 分工、调查、讨论和交接；
7. Checker 核验关键交付；
8. Founder OS 归并证据和分歧；
9. 若需要人判断，生成 Decision Case；
10. 用户决定后系统继续执行；
11. 结果验证并更新上下文。

## 12.3 邀请外部 Agent

1. 用户选择群聊；
2. 选择邀请外部 Agent；
3. 输入 Agent 或所有者标识/邀请链接；
4. 展示所有者、能力、运行位置、价格和权限要求；
5. Agent Owner 确认；
6. 双方确认资源范围和有效期；
7. 授权凭证生成；
8. Agent 加入群聊；
9. 系统记录访问和操作；
10. 任务结束后自动到期或撤销权限。

## 12.4 从市场安装 Agent

1. 用户浏览市场；
2. 查看能力、限制、测试、价格和权限；
3. 选择试用或购买；
4. 系统展示安装配置；
5. 用户授权所需工具和数据；
6. 创建安装实例；
7. 用户将 Agent 加入个人空间或群聊；
8. 监控成本、表现和版本；
9. 可更新、回滚、暂停或卸载。

## 12.5 Decision Case 决策

1. 系统识别需要人介入；
2. 自动恢复相关目标、项目、历史决定和证据；
3. 调用必要的调查/核验 Agent；
4. 形成事实、推断、未知和分歧；
5. 构建方案和机会成本；
6. 展示唯一需要人回答的核心问题；
7. 用户作出决定；
8. 决策被编译成 Policy / Authorization / Task；
9. 系统执行并验证；
10. 结果进入 Outcome Learning。

# 13. MVP 范围与版本规划

## 13.1 MVP 范围原则

Agent 群聊是 Founder OS 的正式产品能力，不应被排除在首发体验之外。Agent 市场是长期核心模块，首发必须建立 Agent 注册、能力描述、安装和私有目录基础，但不要求第一版就完成公开交易平台、开发者结算和大规模审核体系。

- 创始人目标能否被系统理解并转化为约束；

# 15. 非功能需求

## 15.1 性能
- 桌面应用冷启动和主界面加载应保持可接受的桌面应用体验；
- 本地项目索引应支持增量更新；
- 群聊消息发送和状态反馈应及时；
- 长任务必须后台运行，不阻塞 UI；
- Agent 运行状态应区分排队、运行、等待、失败和超时；
- 不得把模型生成延迟伪装成系统已完成。

具体毫秒级指标需在技术选型和原型测试后冻结。

## 15.2 可靠性
- 任务必须有唯一 ID 和幂等处理策略；
- 重试不得造成重复外部操作；
- 长任务必须支持取消或说明不可取消原因；
- 外部 Agent 离线时必须有超时、重试和升级机制；
- 群聊消息和任务状态应支持恢复；
- 关键授权撤销应尽快生效；
- 关键决策和审计数据必须有备份策略。

## 15.3 安全
- 最小权限；
- 默认私有；
- 显式共享；
- 可撤销授权；
- 传输和存储保护；
- 敏感操作服务端二次校验；
- 外部 Agent 沙盒或隔离执行；
- 工具调用审计；
- 秘密和凭证不进入普通群聊消息；
- 版本升级重新评估权限变化。

## 15.4 隐私
- 明确本地与云端数据边界；
- 用户可查看连接器和 Agent 可访问范围；
- 用户可撤销授权；
- 外部 Agent 不默认获得私人记忆；
- 群聊内容的数据使用规则必须清晰；
- 数据保留期限可配置；
- 支持数据导出和删除；
- 不默认使用用户内容训练第三方 Agent。

## 15.5 可扩展性
- Agent Adapter 与业务逻辑解耦；
- Agent Package 有版本和兼容性声明；
- 群聊、任务、证据和 Decision Case 使用稳定 ID；
- 外部 Agent 能力差异通过 Capability Manifest 表达；
- 市场商品和运行实例分离；
- 可替换模型、Harness、协作平台和运行环境。

## 15.6 可观测性
系统应能观察：
- Agent 运行状态；
- 任务成功/失败；
- 调用成本；
- 工具执行；
- 授权使用；
- 核验结果；
- 升级次数；
- 交接延迟；
- 市场 Agent 的版本和质量变化。

可观测性用于系统治理，不应转化为对用户个人行为的隐性监控。

# 16. 指标体系

## 16.1 北极星指标

**每周由 Founder OS 促成、经用户认可且产生可验证进展的有效注意力承诺数。**

有效进展包括：
- 完成关键交付；
- 验证关键假设；
- 降低重大风险；
- 作出必要决策；
- 避免无价值工作；
- 及时停止错误方向。

不能用任务数量或 Agent 完成数量替代。

## 16.2 核心指标

| 指标 | 定义 | 目标方向 |
|---|---|---|
| Time-to-Orientation | 打开产品到理解最重要事项的时间 | 下降 |
| Context Recovery Time | 切回项目恢复有效工作所需时间 | 下降 |
| Human Escalation Precision | 进入 Needs You 后用户认为确实需要自己处理的比例 | 上升 |
| Unnecessary Interruptions | 用户标记为不必要的打断 | 下降 |
| Decision Preparation Time | 形成可判断材料所需时间 | 下降 |
| Agent Silent Resolution Rate | 无需人介入且通过抽样验证的任务比例 | 上升 |
| Verification Pass Rate | 按验收标准通过的交付比例 | 上升 |
| Evidence Coverage | 关键结论具有可追溯证据的比例 | 上升 |
| Policy Compliance | Agent 执行符合授权和约束的比例 | 上升 |
| Collaboration Completion | 群聊任务按标准完成的比例 | 上升 |
| Cross-Agent Handoff Success | Agent 交接成功率 | 上升 |
| External Agent Trust | 外部 Agent 的权限违规和投诉率 | 下降 |
| Marketplace Retention | 安装后持续使用的 Agent 比例 | 适度上升 |
| Agent Outcome Quality | 按任务类型评估的真实结果质量 | 上升 |

## 16.3 不应作为成功指标

- Agent 总数；
- 群聊消息数量；
- 用户打开群聊次数；
- 模型生成字数；
- 用户点击确认的速度；
- 用户接受 AI 建议的比例；
- 市场下载量单一指标；
- 首页停留时间；
- 通知打开率。

这些指标可能奖励更多噪声和不必要的操作。

# 17. 验收场景

## AC-01：多项目变化筛选
Given 用户有三个项目，分别出现普通进度、客户需求变化和生产故障。  
When 系统收到三条观察。  
Then 普通进度进入 Digest，客户需求进入 Attention，生产故障按风险规则升级；首页不得将三条信息同等展示。

## AC-02：目标编译
Given 用户输入自然语言目标。  
When Intent Compiler 处理。  
Then 系统生成目标、指标、约束、范围、非目标和升级条件草案，并区分推断与待确认字段；未确认的重要约束不得自动生效。

## AC-03：Agent 群聊
Given 用户创建一个研究任务并添加多个 Agent。  
When Agent 在群聊中讨论。  
Then 每条消息显示明确身份；支持 @、引用和线程；群聊可创建任务；系统可生成摘要、分歧和未决问题。

## AC-04：执行与核验分离
Given 执行 Agent 提交交付物。  
When Checker 核验。  
Then Checker 按原始验收标准检查；证据不足不能标记 Verified；不通过项可以退回修复。

## AC-05：Decision Case
Given 多 Agent 发现一个会改变资源配置的冲突。  
When Founder OS 判断需要人介入。  
Then 系统生成 Decision Case，展示相关目标、证据、分歧、选项、机会成本和具体问题；不要求用户阅读完整群聊。

## AC-06：授权边界
Given Agent 具有只读和内部任务创建权限。  
When Agent 尝试发送外部邮件或改变预算。  
Then 系统阻止操作并按策略请求授权；Agent 不得通过提示词或群聊自行提升权限。

## AC-07：外部 Agent 邀请
Given 用户邀请另一用户拥有的 Agent。  
When 邀请被接受。  
Then Agent 只能访问明确授权的群聊和资源；不得自动读取任一方私人记忆；授权有期限并可撤销。

## AC-08：外部 Agent 撤销
Given Agent 正在共享空间工作。  
When 所有者或有权管理员撤销授权。  
Then 后续访问和操作被拒绝；系统记录撤销事件；已产生的合法交付记录按数据策略保留。

## AC-09：Marketplace 安装
Given 用户选择一个 Agent Package。  
When 用户安装。  
Then 系统展示能力、限制、版本、运行位置、权限和价格；安装后生成独立实例；用户可以停用、更新或卸载。

## AC-10：市场版本权限变化
Given 已安装 Agent 发布新版本并新增权限。  
When 用户查看更新。  
Then 系统明确展示权限差异；未重新授权前不得使用新增权限。

## AC-11：Agent 离线
Given 任务分配给外部 Agent。  
When Agent 超时或离线。  
Then 任务状态变为 Waiting / Blocked；系统按策略重试、建议替代 Agent 或升级，不得伪装任务已完成。

## AC-12：历史决策冲突
Given 历史决策限制定制项目不得影响核心产品里程碑。  
When 新销售机会出现资源冲突。  
Then 系统识别冲突，计算影响并提出选项；未经有权人批准不得覆盖原约束。

## AC-13：结果不等于任务完成
Given Agent 按需求完成一项功能。  
When 业务数据未达到目标。  
Then 系统不得将目标标记为成功；应保留任务完成状态和业务结果状态的区别。

## AC-14：规则沉淀
Given 某类问题已被用户确认并重复出现。  
When 系统建议生成自动检查或 Policy。  
Then 用户可以查看来源、适用范围、版本和失效条件；确认后规则才生效。

## AC-15：数据与审计
Given 外部 Agent 参与项目。  
When 用户查看审计。  
Then 用户能看到 Agent 所有者、授权范围、访问资源类别、执行操作、费用和结果。

# 18. 风险与缓解策略

| 风险 | 影响 | 缓解 |
|---|---|---|
| 产品范围过大 | 首发无法交付 | P0 聚焦核心闭环；市场先做 Registry，公开交易后置 |
| 群聊退化成消息噪声 | 用户负担增加 | 目标驱动群聊、摘要、任务化和 Decision Case |
| Agent 结论同源错误 | 错误被多数意见放大 | 来源追溯、独立证据和反方验证 |
| Agent 权限混乱 | 越权和数据泄露 | 身份、所有权、权限、授权凭证和审计分离 |
| 外部 Agent 不稳定 | 任务中断 | Adapter、超时、重试、替代 Agent 和人工接管 |
| 市场商品质量不一 | 用户不信任 | 能力声明、测试、试用、版本、评价和下架机制 |
| 过度审查 | 成本和延迟上升 | 重复问题沉淀为规则、静态检查和自动测试 |
| 目标编译错误 | Agent 放大错误目标 | 重要目标确认、版本和冲突检查 |
| 平台锁定 | 外部服务变化影响产品 | 自有数据模型和 Adapter 层 |
| 记忆过期 | 旧规则持续约束新业务 | 有效期、复核日期、冲突和失效机制 |
| 市场恶意 Agent | 数据外传或工具滥用 | 沙盒、最小权限、审核、审计和紧急下架 |

# 20. 产品决策边界与待验证事项

## 20.1 已冻结

- Founder OS 是创始人的 AI 组织操作系统；
- 核心不是项目管理或 Agent Dashboard；
- Decision Case 是人类关键判断入口；
- Agent 群聊是正式产品模块；
- 外部用户拥有的 Agent 必须能够在明确授权下参与协作；
- Agent Marketplace 是长期核心模块；
- 首发建立 Agent Registry 和 Package 基础；
- Agent 身份、所有权、权限和决策权必须分离；
- Intent Compiler、Decision Authority Graph、Validation Architecture 是核心能力；
- Pachat 是可接入的外部协作层，不是唯一后端；
- 不允许执行 Agent 自证关键交付完成；
- 不默认监控用户行为；
- 重要目标和约束必须可追溯、可更新、可撤销。

## 20.2 必须通过技术 Spike 验证

- macOS 桌面技术栈与本地权限模型；
- Agent Adapter 的统一输入输出协议；
- MCP、API、Webhook、CLI 和 Harness 的接入边界；
- Pachat 可用接口、消息读取、任务触发和结果回传能力；
- 群聊消息与任务状态的实时同步方式；
- 外部 Agent 授权凭证和撤销机制；
- 多租户数据隔离；
- Agent Package 的运行隔离与依赖管理；
- 市场计费和成本归属；
- 本地 Agent 与云端 Agent 的混合运行模式。

## 20.3 必须通过用户验证

- 首发用户是否愿意把群聊作为 Agent 协作空间；
- 用户是否需要邀请其他人的 Agent；
- 哪些 Agent 能力最有真实付费需求；
- 用户更偏好购买 Agent 服务还是购买 Agent Package；
- 用户愿意开放哪些数据给外部 Agent；
- Decision Case 的信息密度是否足以支持判断；
- Founder OS 能否明显减少上下文恢复和无效打扰；
- Agent Marketplace 是否能产生持续使用而非一次性安装。

# 21. 最终产品定义

Founder OS 不是一个让用户更方便地使用 AI 的工具，也不是一个把多个 Agent 放在同一屏幕里的管理面板。

它是一个以创始人意图为中心、以 Agent 协作为执行方式、以授权和验证为治理基础的 AI 组织操作系统。

它允许创始人：
- 定义目标；
- 建立组织上下文；
- 连接自己的 Agent；
- 邀请其他人的 Agent；
- 在群聊中组织多 Agent 协作；
- 从市场获得专业 Agent 能力；
- 将决策转化为可执行约束；
- 让 AI 在授权范围内自主推进；
- 只在关键问题上介入；
- 通过证据验证实际结果；
- 将经验持续沉淀为组织能力。

**最终目标：让一个人能够组织和经营一个由多个 AI Agent 协作执行的组织，同时不丢失对目标、方向、权限和结果的控制。**

# 附录 B：首发版本的最小完整闭环

首发版本必须至少跑通以下闭环：

1. 用户建立一个项目目标；
2. Founder OS 将目标编译为结构化目标和约束；
3. 用户将两个或多个 Agent 加入一个群聊；
4. 用户提出一个真实任务；
5. Agent 在群聊中讨论、分工和执行；
6. 至少一个交付由独立核验角色检查；
7. Founder OS 整理证据、分歧和结果；
8. 需要人判断时生成 Decision Case；
9. 用户作出决定；
10. 决策被转化为下一步任务和授权；
11. Agent 在授权范围内继续执行；
12. 系统记录结果并更新项目上下文。

若首发版本只能展示 Agent 对话，却不能完成任务、核验、决策和结果回写，则不构成 Founder OS 的有效 MVP。

# 附录 C：产品不可妥协原则

1. 不以 Agent 数量作为产品价值。
2. 不以消息数量作为协作质量。
3. 不以任务完成数量替代目标达成。
4. 不以多数 Agent 意见替代证据。
5. 不以执行权限替代决策权。
6. 不以安装 Agent 等同于获得其所有权。
7. 不以群聊参与等同于获得数据访问权限。
8. 不以历史记忆等同于永久有效的规则。
9. 不以更多审批等同于更安全。
10. 不以更多 Review 等同于更高质量。
11. 不把用户变成 Agent 的逐条消息审核员。
12. 不把 Founder OS 做成另一个任务管理器或通用聊天工具。
